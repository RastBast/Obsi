# Как правильно работать с SQL-транзакциями?

## Вопрос

Как организовать `Begin/Commit/Rollback`, что даёт isolation level и как обрабатывать deadlock/serialization failure?

## Краткий ответ

Транзакцию начинают с context, сразу откладывают `Rollback`, все операции выполняют через `Tx`, затем вызывают `Commit`. Уровень изоляции определяет видимые конкурентные эффекты, но фактическая поддержка зависит от БД/драйвера. Retry допустим для определённых ошибок и только для повторяемой логики.

## Развёрнутый ответ мидла

```go
tx, err := db.BeginTx(ctx, &sql.TxOptions{})
if err != nil { return err }
defer tx.Rollback() // после Commit обычно безопасно вернёт sql.ErrTxDone

if _, err := tx.ExecContext(ctx, q1, a); err != nil { return err }
if _, err := tx.ExecContext(ctx, q2, b); err != nil { return err }
return tx.Commit()
```

Нельзя внутри логической транзакции случайно вызвать `db.Exec`: запрос уйдёт через другое соединение и вне Tx. Транзакцию держат короткой, не делают в ней долгий HTTP-вызов.

`Commit` сам может вернуть ошибку; успех нельзя объявлять до успешного Commit.

## Развёрнутый ответ сеньора: все тонкости

ACID и названия isolation levels не гарантируют идентичное поведение всех СУБД. Нужно знать MVCC/locking конкретной БД и аномалии: dirty/non-repeatable read, phantom, lost update, write skew. `Serializable` может завершать одну из транзакций ошибкой — приложение обязано быть готово повторить её.

Retry охватывает всю транзакцию от Begin и использует новую Tx. Он ограничен попытками, общим deadline, backoff/jitter и классификацией vendor error codes. Функция retry не должна выполнять необратимые внешние side effects внутри попытки. Для публикации события применяют transactional outbox, а внешний consumer делает идемпотентным.

Deadlock — нормальный возможный исход конкурентного locking, а не обязательно баг БД. Снижают вероятность единым порядком обновления строк, короткими Tx и подходящими индексами; victim повторяют по политике.

Context cancellation во время Commit создаёт тонкую неопределённость результата в распределённом смысле: клиент мог не получить подтверждение, хотя БД зафиксировала. Для критических операций используют idempotency key и возможность reconcile.

Не передают `*sql.Tx` произвольным параллельным goroutine: одна Tx обычно использует одно connection и операции/протокол могут не поддерживать ожидаемый параллелизм.

## Если забыл / Простыми словами

Шаблон: **Begin → defer Rollback → только tx.Query/Exec → Commit и проверить ошибку**. Isolation — договор о конкуренции; transient retry должен повторять всю чистую/идемпотентную транзакцию.

Представь базу как общий архив, которым одновременно пользуются многие сотрудники. Соединения, блокировки и транзакции определяют, кто и когда может читать или менять записи. Правильный протокол защищает данные от противоречий и не даёт одному запросу остановить остальных.
