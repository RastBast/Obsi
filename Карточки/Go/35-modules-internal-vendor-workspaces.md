# Как Go управляет модулями и зависимостями?

## Вопрос

Что задают `go.mod` и `go.sum`, чем module отличается от package, для чего нужны `internal`, `vendor` и `go work`?

## Краткий ответ

Module — версионируемая коллекция packages с путём из `go.mod`; package — единица компиляции в каталоге. `go.sum` фиксирует криптографические суммы загруженных модулей. `internal` ограничивает импорт, `vendor` хранит копии зависимостей, `go work` связывает локальные модули без постоянных `replace`.

## Развёрнутый ответ мидла

`go.mod` содержит module path, версию Go, `require`, а при необходимости `replace`/`exclude`. `go mod tidy` добавляет нужные и удаляет лишние зависимости согласно импортам и тестам.

`go.sum` — не lockfile в смысле точного графа всех сборок: выбранные версии задаются алгоритмом modules и `go.mod`, а суммы проверяют целостность содержимого.

Код под `a/internal/x` могут импортировать только пакеты внутри дерева, корнем которого является родитель `a`. Это enforce-ится toolchain.

Semantic Import Versioning требует `/v2` в module path для major v2+ (кроме особых legacy-механизмов).

## Развёрнутый ответ сеньора: все тонкости

Minimal Version Selection выбирает максимальную требуемую версию каждого module path среди требований графа, а не решает SAT как некоторые package managers. Retracted/deprecated версии и несовместимые major paths требуют понимания metadata и release policy.

`replace` полезен локально или для временного fork, но может скрыть зависимость от незапушенного пути. Перед релизом проверяют, что replace воспроизводим. Workspace (`go.work`) удобен для совместной разработки нескольких модулей и обычно не должен случайно менять поведение CI/релиза.

`vendor` повышает контроль/offline reproducibility, но требует `go mod vendor` и политики обновления; он не заменяет проверку лицензий и уязвимостей. Supply-chain включает module proxy/checksum database, private module настройки и инструменты вроде `govulncheck`.

Версия в директиве `go` влияет на языковую семантику и поведение toolchain, а не только документирует минимальную версию. Директива `toolchain` может управлять рекомендуемым/выбираемым toolchain в современных Go.

Много маленьких модулей внутри одного repo усложняют versioning. Module boundary выбирают по независимости релизов и потребителей, package boundary — по связности кода.

## Если забыл / Простыми словами

**Module версионируется, package импортируется.** `go.mod` описывает граф и правила, `go.sum` проверяет содержимое, `internal` защищает границу, `go work` помогает локальной мультимодульной разработке.

### Аналогия и объяснение

**Module версионируется, package импортируется.** `go.mod` описывает граф и правила, `go.sum` проверяет содержимое, `internal` защищает границу, `go work` помогает локальной мультимодульной разработке.

Представь, что это одно из правил языка и стандартной библиотеки: оно задаёт, как программа хранит данные или выполняет действие. Понимание правила помогает не угадывать поведение кода, а заранее предсказывать результат, находить ошибки и выбирать более простой API.
