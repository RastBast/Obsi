# Когда использовать context.WithCancelCause?

## Вопрос

Чем причина отмены отличается от `ctx.Err()` и как не потерять первичную ошибку группы задач?

## Краткий ответ

`WithCancelCause` позволяет отменить context с конкретной ошибкой; `context.Cause(ctx)` возвращает её, а `ctx.Err()` остаётся общей категорией canceled/deadline. Это помогает диагностике, но результат операции всё равно должен возвращаться обычным `error`.

## Развёрнутый ответ мидла

- Создатель вызывает `cancel(err)` и освобождает ресурсы.
- Дочерние contexts наследуют причину по правилам первой произошедшей отмены.
- Cause не кладут в Value и не используют как скрытый канал всех ошибок.
- Caller проверяет собственный returned error и при необходимости Cause.

## Развёрнутый ответ сеньора: все тонкости

- Гонки нескольких cancel означают, что контракт должен определить важность первой причины.
- Причина может содержать sensitive data и распространиться дальше, чем обычный log context.
- Deadline cause удобен для различения локальной политики и родительской отмены.
- Library API не должно требовать Cause там, где поддерживается обычный Context от caller.

### Дополнительное техническое объяснение

Causal cancellation связывает cancellation signal с error payload, наследуемым context tree. `Err` сохраняет sentinel semantics, а `Cause` предоставляет diagnostic provenance; error propagation и API contract остаются явными return values.

## Если забыл / Простыми словами

Err говорит «отменено», Cause может сказать «почему именно». Не заменяй им возврат результата.

### Аналогия и объяснение

Обычная отмена похожа на красную лампу «стоп». Cause добавляет записку: остановились из-за ошибки чтения, shutdown или другой причины. Основной ответ функции всё равно возвращается обычным способом.
