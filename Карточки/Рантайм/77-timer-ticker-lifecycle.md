# Как управлять Timer и Ticker без утечек и гонок?

## Вопрос

Когда применять Timer/Ticker, зачем вызывать Stop и какие сложности есть у Reset?

## Краткий ответ

Timer даёт одно событие, Ticker — периодические. Владелец останавливает их, когда события больше не нужны. Reset/Stop имеют семантику, зависящую от состояния и версии Go; код следует документации minimum version и не допускает конкурентного управления без протокола.

## Развёрнутый ответ мидла

- `time.After` удобно для единичного select, Timer — для управления lifecycle.
- Ticker может пропускать/сливать ticks, если consumer не успевает; это не очередь всех интервалов.
- `defer ticker.Stop()` ставят после создания в ограниченной функции.
- Для scheduler по wall time отдельно учитывают clock jumps и DST.

## Развёрнутый ответ сеньора: все тонкости

- Старые советы о drain канала Timer могут отличаться для новых реализаций; фиксируют версию и читают docs.
- Callback `AfterFunc` выполняется в отдельной goroutine и требует синхронизации с Stop/Reset.
- Тысячи индивидуальных timers имеют runtime cost; иногда нужен общий scheduler/heap.
- Периодическую задачу защищают от overlap, если предыдущий запуск дольше интервала.

### Дополнительное техническое объяснение

Runtime timer heap планирует wakeups; Ticker delivery допускает coalescing. Lifecycle operations Stop/Reset координируются с channel/callback delivery по versioned API semantics, а job scheduler отдельно определяет overlap и drift policy.

## Если забыл / Простыми словами

Timer — один сигнал, Ticker — повтор. У каждого должен быть владелец остановки и политика медленного consumer.

### Аналогия и объяснение

Будильник звонит один раз, метроном — регулярно. Если работу по удару не успевают закончить, метроном не обязан хранить все пропущенные удары. При уходе из комнаты устройство нужно выключить.
