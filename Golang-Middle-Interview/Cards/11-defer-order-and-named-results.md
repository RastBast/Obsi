# Как работает defer?

## Вопрос

Когда вычисляются аргументы `defer`, в каком порядке выполняются отложенные вызовы и как они взаимодействуют с именованными результатами?

## Краткий ответ

Аргументы и receiver отложенного вызова вычисляются в момент выполнения `defer`, сам вызов — перед выходом из текущей функции. Несколько defer выполняются в обратном порядке. Deferred closure может читать и менять именованный результат.

## Развёрнутый ответ мидла

```go
func f() (n int) {
    n = 1
    defer func() { n++ }()
    defer fmt.Println(n) // аргумент n уже вычислен: напечатает 1
    n = 10
    return              // closure сделает результат 11
}
```

При выходе сначала выполнится последний зарегистрированный `defer`. Они срабатывают при обычном `return` и при раскрутке стека из-за panic, но не гарантируются при принудительном завершении процесса, например `os.Exit`.

Типичные применения:

```go
f, err := os.Open(name)
if err != nil { return err }
defer f.Close()
```

`defer` ставят сразу после успешного захвата ресурса, чтобы очистка находилась рядом и выполнялась на всех путях возврата.

## Развёрнутый ответ сеньора: все тонкости

В `defer obj.Method(arg)` и `obj`, и `arg` вычисляются немедленно. Closure, наоборот, захватывает переменные; какое именно значение она увидит, зависит от дальнейших присваиваний и правил захвата. Это частый источник разницы между `defer fmt.Println(x)` и `defer func(){ fmt.Println(x) }()`.

Ошибку `Close` иногда нельзя игнорировать, особенно при записи: буферизация может отложить ошибку до закрытия. Тогда именованный `err` аккуратно обновляют, не затирая более раннюю ошибку:

```go
defer func() {
    if closeErr := w.Close(); err == nil { err = closeErr }
}()
```

Нужно избегать defer внутри долгого цикла, если функция не возвращается: ресурсы накопятся до конца функции. Цикл выносят в маленькую функцию или закрывают ресурс явно на каждой итерации.

Современный компилятор оптимизирует многие defer, поэтому отказываться от них из-за старого мифа о высокой цене не нужно. На реально горячем пути решение принимают по benchmark.

Изменение именованных результатов в defer легально, но скрытая логика ухудшает читаемость. Хорошие случаи — добавление контекста к ошибке, recover или корректная обработка Close; бизнес-логику лучше делать явно.

## Если забыл: что это, зачем и где нужно

Мнемоника: **аргументы сейчас, вызов потом, порядок LIFO**. `defer` нужен прежде всего для освобождения ресурсов, разблокировки mutex, завершения trace/span и локальной обработки panic.
