# Что такое pipeline, fan-out и fan-in?

## Вопрос

Как строятся конвейеры на каналах, как распараллелить этап и как избежать зависания при досрочном завершении consumer?

## Краткий ответ

Pipeline передаёт поток через стадии; fan-out даёт нескольким workers читать общий вход, fan-in объединяет несколько выходов. Каждая стадия должна закрывать свой output после завершения и уметь прекратить send/receive по context, иначе ранний consumer оставит producers заблокированными.

## Развёрнутый ответ мидла

```go
func mapStage(ctx context.Context, in <-chan A) <-chan B {
    out := make(chan B)
    go func() {
        defer close(out)
        for a := range in {
            b := transform(a)
            select {
            case out <- b:
            case <-ctx.Done(): return
            }
        }
    }()
    return out
}
```

Fan-out: несколько workers читают один `in`. Fan-in: отдельная goroutine на каждый input копирует значения в общий `out`; координатор закрывает `out` после `WaitGroup`.

Все потенциально блокирующие send должны учитывать отмену. Иначе consumer, нашедший нужный результат и вышедший, оставит upstream зависшим.

## Развёрнутый ответ сеньора: все тонкости

Конвейер — не самоцель. Для короткой синхронной последовательности обычные вызовы проще и дешевле. Pipeline полезен при потоковой обработке, естественной конкуренции стадий или необходимости bounded buffering между разными скоростями.

Буфер между стадиями задаёт backpressure и сглаживает bursts, но также увеличивает максимальную память и end-to-end latency. Little’s Law помогает связать throughput, latency и размер очереди; настройки измеряют под реальной нагрузкой.

Fan-out безопасен для независимых элементов. Если элементы одного ключа должны сохранять порядок, применяют consistent sharding по ключу. Fan-in разрушает глобальный порядок, если не добавлен явный sequence/reordering.

Ошибка одной стадии должна отменить всю связную группу, иначе другие продолжают блокироваться или тратить ресурсы. Удобна комбинация errgroup + context, но закрытие каналов всё равно требует единого владельца и корректного порядка.

Передача pointer/slice по каналу часто воспринимается как передача владения. Если sender продолжает менять буфер после send, возникает race. Контракт должен запрещать изменение либо выполнять копию.

## Если забыл: что это, зачем и где нужно

Fan-out = **один поток распределить**, fan-in = **несколько потоков объединить**. Главный вопрос не схема стрелок, а что произойдёт при отмене, ошибке, медленной стадии и закрытии.
