# Когда использовать errgroup и semaphore?

Как запустить несколько связанных задач, отменить остальные при ошибке и ограничить параллелизм?

===

@input

---

## Краткий ответ

`errgroup.WithContext` связывает группу goroutine: возвращает первую ненулевую ошибку и отменяет context группы. `SetLimit` или weighted semaphore ограничивает активную работу. Нужно по-прежнему правильно передавать context и не допускать блокирующих send вне отмены.

---

## Развёрнутый ответ мидла

```go
g, ctx := errgroup.WithContext(ctx)
g.SetLimit(8)
for _, item := range items {
    item := item
    g.Go(func() error {
        return process(ctx, item)
    })
}
if err := g.Wait(); err != nil {
    return err
}
```

`golang.org/x/sync/errgroup` — внешний модуль, хотя поддерживается Go team. Он удобнее `WaitGroup`, когда нужны ошибки и общая отмена.

Semaphore подходит, если goroutine имеют другой lifecycle, но доступ к дорогому ресурсу нужно ограничить. Acquire должен учитывать context, Release обычно ставят в defer после успешного Acquire.

---

## Развёрнутый ответ сеньора: все тонкости

`errgroup` возвращает первую наблюдённую ошибку, а не все ошибки и не обязательно хронологически «главную». Если нужен полный отчёт, ошибки собирают отдельно с синхронизацией или используют другой контракт. Ошибка context после чужой ошибки не должна затереть первопричину на внешней границе.

При `SetLimit` вызов `Go` может блокироваться до свободного слота. Нельзя менять limit, пока в группе активны goroutine. Если producer сам должен отменяться во время ожидания слота, нужно внимательно проверить семантику используемой версии и при необходимости применить semaphore с `Acquire(ctx, weight)`.

Weighted semaphore полезен, когда задачи потребляют разное количество ресурса. Вес не должен превышать ёмкость, иначе Acquire никогда не выполнится без отмены. Освобождают ровно успешно захваченный вес.

Лимит должен согласовываться с нижним пулом: 100 goroutine перед SQL pool из 10 соединений лишь создадут очередь в другом месте. Часто лучше один осмысленный backpressure boundary.

Structured concurrency означает, что функция не возвращается, пока созданные ею задачи не завершены/отменены. `errgroup` помогает, но goroutine, запущенные внутри задачи в обход группы, снова становятся неуправляемыми.

## Если забыл / Простыми словами

`WaitGroup` ждёт, `errgroup` **ждёт + переносит первую ошибку + отменяет siblings**. Semaphore ограничивает доступ к ресурсу. В обоих случаях context должен доходить до реальной блокирующей операции.

### Аналогия и объяснение

`WaitGroup` ждёт, `errgroup` **ждёт + переносит первую ошибку + отменяет siblings**. Semaphore ограничивает доступ к ресурсу. В обоих случаях context должен доходить до реальной блокирующей операции.

Представь runtime как диспетчера, который распределяет работу и память между множеством исполнителей. Если не учитывать правила диспетчера, задачи могут мешать друг другу, ждать бесконечно или расходовать ресурсы. Поэтому всегда нужно понимать владельца состояния, момент синхронизации и условие завершения.
