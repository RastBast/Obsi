# Что размещается на стеке, а что в куче?

По каким правилам Go размещает данные на stack/heap, что такое escape analysis и всегда ли возврат указателя означает ошибку?

===

@input

---

## Краткий ответ

Размещение выбирает компилятор по escape analysis. Если значение может жить дольше текущего stack frame или его безопасность нельзя доказать, оно обычно уходит в heap. Возвращать указатель на локальную переменную безопасно: компилятор продлит её жизнь.

---

## Развёрнутый ответ мидла

```go
func newInt() *int {
    x := 42
    return &x // безопасно; x обычно escape в heap
}
```

В Go нет висячего указателя на уничтоженный stack frame в обычном безопасном коде. Runtime и компилятор обеспечивают корректное время жизни.

Посмотреть решения:

```bash
go build -gcflags='-m=2' ./...
```

Heap allocations увеличивают работу GC, но сами по себе не являются багом. Сначала находят горячее место профилем/benchmark, потом оптимизируют.

Стек goroutine начинается небольшим и растёт по необходимости.

## Развёрнутый ответ сеньора: все тонкости

Escape — свойство использования, а не типа. Один и тот же struct в одном месте будет на stack, в другом — в heap. Передача в interface, closure, неизвестный вызов, слишком большой объект или хранение указателя могут повлиять на решение, но конкретные эвристики компилятора меняются.

`-m` показывает не только «moved to heap», но и путь утечки параметра. Однако оптимизации, inlining и контекст вызова влияют на финальный результат. Не стоит менять публичный API только ради одного сообщения без измерения эффекта.

Stack allocation дешёвая и освобождается вместе с frame; heap требует GC. Но огромный stack object увеличивает копирование/рост стека и может быть хуже. Pooling тоже не бесплатна и может удерживать память.

Возврат значения вместо указателя иногда уменьшает escape, но крупное значение может копироваться, а компилятор умеет elision/inlining. Семантика владения важнее предположения о копии.

`unsafe.Pointer`/`uintptr` нарушают обычные гарантии, если скрывают указатель от GC или сохраняют его через перемещение стека. `uintptr` — число, а не GC-tracked pointer; его нельзя использовать как долговременное хранилище адреса.

## Если забыл / Простыми словами

Не говори «`new` всегда heap, локальная переменная всегда stack» — это неверно. Правильный ответ: **решает escape analysis; возврат адреса безопасен; оптимизируем только измеренный hot path**.
