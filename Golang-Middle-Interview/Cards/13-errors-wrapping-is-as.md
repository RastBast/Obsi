# Как проектировать и оборачивать ошибки в Go?

## Вопрос

Когда использовать sentinel error, типизированную ошибку, `%w`, `errors.Is` и `errors.As`? Почему нельзя сравнивать обёрнутые ошибки через `==`?

## Краткий ответ

Ошибку оборачивают `fmt.Errorf("контекст: %w", err)`, сохраняя причинную цепочку. Категорию проверяют `errors.Is`, данные типизированной ошибки извлекают `errors.As`. `==` видит только конкретное верхнее значение и обычно не проходит через обёртки.

## Развёрнутый ответ мидла

```go
var ErrNotFound = errors.New("not found")

func load(id string) error {
    err := repoGet(id)
    if err != nil {
        return fmt.Errorf("load user %q: %w", id, err)
    }
    return nil
}

if errors.Is(err, ErrNotFound) { /* 404 */ }

var pathErr *os.PathError
if errors.As(err, &pathErr) { /* используем pathErr.Path */ }
```

 `%v` добавляет текст, но не сохраняет unwrap-цепочку; `%w` сохраняет. Ошибку обычно обрабатывают один раз: либо добавляют контекст и возвращают, либо преобразуют в результат на границе. Логирование на каждом слое создаёт дубли.

Текст ошибки пишут с маленькой буквы и без точки, чтобы его можно было составлять с внешним контекстом.

## Развёрнутый ответ сеньора: все тонкости

Sentinel (`var ErrX`) делает категорию частью API: потребители начинают зависеть от неё. Типизированная ошибка подходит, когда нужны структурированные поля. Иногда лучше скрыть внутреннюю ошибку хранилища и перевести её в доменную категорию, чтобы замена БД не ломала вызывающий код.

`errors.Is` проходит цепочку `Unwrap()` и учитывает пользовательский метод `Is(error) bool`; `errors.As` ищет присваиваемый тип и может учитывать `As(any) bool`. `errors.Join` представляет несколько причин, и обход должен рассматриваться как дерево. Нельзя предполагать только одну линейную причину.

Оборачивание `%w` раскрывает возможность проверки внутренней причины и тем самым может стать частью публичного контракта. Иногда намеренно возвращают новую доменную ошибку без unwrap, сохранив исходную только в логах/telemetry, если её нельзя раскрывать наружу.

Нельзя определять логику по `strings.Contains(err.Error(), ...)`: текст нестабилен и предназначен человеку. Для retryability, HTTP-кода или gRPC-кода нужна явная классификация.

Ошибка может содержать чувствительные данные. Контекст должен помогать диагностике, но не включать токены, пароли и полные персональные данные. Stack trace не является обязательной частью `error`; его обычно захватывает наблюдаемость на границе.

## Если забыл: что это, зачем и где нужно

Модель: **добавь контекст через `%w`; спроси категорию через `Is`; достань поля через `As`**. Ошибка — это не просто строка, а контракт между слоями.
