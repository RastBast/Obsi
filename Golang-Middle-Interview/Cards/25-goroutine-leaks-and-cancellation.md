# Как возникают утечки goroutine и как их предотвращать?

Назовите типичные причины goroutine leak. Как спроектировать завершение фоновой работы и доказать, что goroutine остановится?

===

@input

---

## Краткий ответ

Goroutine утекает, когда навсегда ждёт канал, lock, I/O или отправляет результат, который никто не читает. У каждой goroutine должен быть владелец, условие завершения и путь отмены; блокирующие операции должны наблюдать context или закрытие.

---

## Развёрнутый ответ мидла

Плохой пример:

```go
func first() Result {
    ch := make(chan Result)
    go func() { ch <- slowWork() }()
    return <-anotherSource // worker может навсегда зависнуть на send
}
```

Варианты исправления: буфер результата ёмкости 1, `select` с `ctx.Done()`, обязательное чтение результата или общий structured-concurrency механизм.

```go
select {
case out <- result:
case <-ctx.Done():
    return
}
```

Сеть и БД должны получать context/timeout. Канал, который никто не закроет и в который никто не отправит, блокирует receiver навсегда.

---

## Развёрнутый ответ сеньора: все тонкости

Cancellation кооперативна. Даже если outer function вернулась по context, запущенная ею goroutine продолжит жить, пока её конкретная операция не завершится. API без отменяемого I/O требует отдельного lifecycle или отказа от запуска.

Протокол shutdown обычно имеет фазы: перестать принимать работу, отменить producers, дать consumers дренировать допустимый остаток, дождаться `WaitGroup`, затем закрыть ресурсы. Порядок зависит от требований: жёсткая отмена и graceful drain — разные контракты.

Диагностика: метрика числа goroutine, `runtime/pprof` goroutine profile, stack dump, блок-профиль, тесты с ограниченным временем и leak-check библиотеками. Один только рост `runtime.NumGoroutine` шумный: runtime и зависимости имеют собственные фоновые goroutine.

Ticker, subscription, watcher, connection и response body — связанные источники утечек ресурсов. `Ticker.Stop`, unsubscribe, `rows.Close`, `resp.Body.Close` и отмена context должны принадлежать тому же lifecycle.

Нельзя закрывать общий канал со стороны отменяемого consumer, если producers могут продолжить send: будет panic. Часто отдельный `ctx.Done()` безопаснее закрытия data channel.

## Если забыл / Простыми словами

Для каждой `go`-строки задай три вопроса: **кто ждёт результат, кто отменяет, на каком условии она выходит?** Если ответа нет, вероятна утечка.

### Аналогия и объяснение

Для каждой `go`-строки задай три вопроса: **кто ждёт результат, кто отменяет, на каком условии она выходит?** Если ответа нет, вероятна утечка.

Представь runtime как диспетчера, который распределяет работу и память между множеством исполнителей. Если не учитывать правила диспетчера, задачи могут мешать друг другу, ждать бесконечно или расходовать ресурсы. Поэтому всегда нужно понимать владельца состояния, момент синхронизации и условие завершения.
