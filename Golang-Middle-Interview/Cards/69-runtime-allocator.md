# Как в общих чертах устроен аллокатор Go?

## Вопрос

Почему мелкие allocations не обращаются к ОС каждый раз и что дают size classes, spans и per-P caches?

## Краткий ответ

Runtime получает крупные регионы памяти и раздаёт объекты по size classes. Локальные per-P caches уменьшают locks для частых мелких allocations, spans группируют страницы под класс размеров. Точные структуры — implementation detail.

## Развёрнутый ответ мидла

- Запрос округляется до подходящего size class, поэтому фактическая память может быть больше размера объекта.
- Мелкие pointer-free объекты могут обслуживаться специальными оптимизациями.
- Крупные allocations идут отдельным путём и сильнее влияют на heap/RSS.
- Освобождение управляется GC; приложение не вызывает `free` для обычных Go objects.

## Развёрнутый ответ сеньора: все тонкости

- Fragmentation бывает внутренней из-за округления и внешней из-за распределения spans.
- Heap profile семплирует requested allocation, а RSS отражает также retained/scavenged pages и metadata.
- Scavenger возвращает неиспользуемые страницы ОС асинхронно; падение heap не обязано мгновенно снижать RSS.
- Pooling объектов разных размеров может ухудшить locality и удерживать oversized buffers.

## Если забыл: что это, зачем и где нужно

Runtime берёт память оптом и быстро раздаёт кусками подходящего размера. Оптимизируют allocation rate по профилю.

## Подробное объяснение простыми словами

Вместо похода на фабрику за каждой коробкой склад заранее получает паллеты стандартных размеров. Выдать коробку быстро, но предмет иногда занимает коробку больше себя, а пустая паллета не сразу возвращается фабрике.

## Подробное объяснение техническими терминами

Allocator использует size-class segregated spans и per-P caches для снижения synchronization. GC reclaim изменяет object liveness, а scavenger управляет physical page return; heap accounting и process RSS поэтому расходятся.
