# Как тестировать зависимости: mock, stub или fake?

## Вопрос

Чем отличаются mock, stub и fake, где объявлять интерфейсы и почему «интерфейс для каждой структуры» ухудшает Go-код?

## Краткий ответ

Stub возвращает заранее заданные данные, mock проверяет ожидаемые взаимодействия, fake имеет упрощённую рабочую реализацию. Маленький интерфейс обычно объявляет потребитель по нужному поведению; интерфейс не нужен, если нет второй реализации или границы тестирования.

## Развёрнутый ответ мидла

```go
type UserFinder interface {
    Find(ctx context.Context, id string) (User, error)
}

type Service struct { users UserFinder }
```

В тесте часто достаточно ручного stub:

```go
type finderFunc func(context.Context, string) (User, error)
func (f finderFunc) Find(ctx context.Context, id string) (User, error) {
    return f(ctx, id)
}
```

Так тест задаёт только нужное поведение без большого mock framework. Constructor injection делает обязательные зависимости явными.

Проверяют результат и побочные эффекты контракта, а не каждую внутреннюю функцию.

## Развёрнутый ответ сеньора: все тонкости

Consumer-owned interface уменьшает связанность: repository не обязан заранее угадывать все способы использования. Интерфейс из одного-двух методов легче реализовать, но «чем меньше, тем всегда лучше» тоже не догма — методы должны выражать цельный контракт.

Mock с точным порядком внутренних вызовов делает тест хрупким к рефакторингу. Interaction testing оправдан для важных side effects: «платёж вызван один раз с idempotency key», «транзакция откатилась». Для сложного repository in-memory fake может дать более устойчивые state-based проверки, но fake обязан достаточно точно моделировать уникальность, транзакции и ошибки, иначе создаёт ложную уверенность.

Не нужно мокать `time.Now`, `rand` или HTTP на уровне глобальных monkey patches. Передают `Clock`, генератор или настраиваемый `http.Client/Transport`; иногда function field проще интерфейса.

Интеграционный тест с настоящей БД ловит то, что mock не моделирует: SQL, isolation, driver conversions. Хорошая пирамида сочетает быстрые unit tests и меньшее число реалистичных integration tests.

Dependency injection в Go обычно делается обычными конструкторами и структурами; runtime DI container/reflection не обязателен и может скрыть граф.

## Если забыл / Простыми словами

Тестируемость получается из **явных зависимостей и маленьких контрактов**, а не из максимума моков. Stub даёт ответ, mock проверяет вызовы, fake реально исполняет упрощённую модель.

### Аналогия и объяснение

Тестируемость получается из **явных зависимостей и маленьких контрактов**, а не из максимума моков. Stub даёт ответ, mock проверяет вызовы, fake реально исполняет упрощённую модель.

Представь, что это одно из правил языка и стандартной библиотеки: оно задаёт, как программа хранит данные или выполняет действие. Понимание правила помогает не угадывать поведение кода, а заранее предсказывать результат, находить ошибки и выбирать более простой API.
