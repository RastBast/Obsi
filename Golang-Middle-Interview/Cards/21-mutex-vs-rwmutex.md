# Когда использовать Mutex, а когда RWMutex?

## Вопрос

Как правильно защищать разделяемое состояние с `sync.Mutex` и когда `RWMutex` действительно полезен?

## Краткий ответ

`Mutex` даёт взаимоисключение и обычно является выбором по умолчанию. `RWMutex` позволяет параллельные читатели, но исключительную запись; он помогает только при подходящем профиле долгих/частых чтений и должен быть подтверждён измерениями.

## Развёрнутый ответ мидла

```go
type Cache struct {
    mu sync.RWMutex
    m  map[string]Value
}

func (c *Cache) Get(k string) (Value, bool) {
    c.mu.RLock()
    defer c.mu.RUnlock()
    v, ok := c.m[k]
    return v, ok
}
```

Все доступы к защищаемому инварианту используют один и тот же lock. Нельзя читать map «без lock, потому что только чтение», если другая goroutine может писать.

Критическую секцию делают короткой: не выполняют под lock медленную сеть и неизвестный callback. `defer mu.Unlock()` обычно безопаснее ручного unlock.

`Mutex` нельзя копировать после первого использования. Его zero value готов к работе.

## Развёрнутый ответ сеньора: все тонкости

`RWMutex` имеет накладные расходы и может быть хуже `Mutex` при коротких секциях, частых записях или небольшом числе CPU. Решение принимают по benchmark с реальным соотношением read/write и contention. Параллельное чтение полезно только если сами данные действительно immutable в этот период.

Go `Mutex` не реентерабелен. Повторный `Lock` той же goroutine приводит к deadlock; runtime не привязывает lock к «владельцу» в удобном для рекурсии смысле. Для нескольких locks нужен постоянный порядок захвата, иначе возможен cycle/deadlock.

Нельзя безопасно «повысить» `RLock` до `Lock`: нужно отпустить read lock, взять write lock и заново проверить условие, потому что состояние могло измениться. Нельзя также полагаться на строгую справедливость планирования.

Копирование защищённого значения под lock должно быть действительно независимым. Возврат map/slice/указателя может выпустить наружу доступ к внутреннему mutable state после unlock. Возвращают копию, immutable snapshot или метод, выполняющий операцию под lock.

`TryLock`/`TryRLock` существуют, но успешный дизайн редко строится на активных попытках; они оправданы только для специфического протокола. Часто блокирующий lock проще и корректнее.

## Если забыл: что это, зачем и где нужно

Mutex защищает **инвариант и все пути доступа**, а не отдельную строку кода. Начинай с `Mutex`; переходи на `RWMutex` только после измерений. Не копируй lock и не вызывай долгий внешний код внутри секции.

## Подробное объяснение простыми словами

Представь runtime как диспетчера, который распределяет работу и память между множеством исполнителей. Если не учитывать правила диспетчера, задачи могут мешать друг другу, ждать бесконечно или расходовать ресурсы. Поэтому всегда нужно понимать владельца состояния, момент синхронизации и условие завершения.
