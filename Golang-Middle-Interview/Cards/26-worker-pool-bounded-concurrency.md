# Как спроектировать worker pool с ограниченной конкуренцией?

Как обработать много задач, не создавая неограниченное число goroutine? Как передать backpressure, ошибки и отмену?

===

@input

---

## Краткий ответ

Создают фиксированное число workers, читающих очередь задач, либо используют semaphore для ограничения активных операций. Размер — лимит ресурса, а не магическое число. Producer должен видеть backpressure/cancellation, а владелец — закрывать очередь и собирать ошибки.

---

## Развёрнутый ответ мидла

```go
func worker(ctx context.Context, jobs <-chan Job, results chan<- Result) error {
    for {
        select {
        case <-ctx.Done():
            return ctx.Err()
        case j, ok := <-jobs:
            if !ok { return nil }
            r, err := process(ctx, j)
            if err != nil { return err }
            select {
            case results <- r:
            case <-ctx.Done(): return ctx.Err()
            }
        }
    }
}
```

Очередь закрывает producer после окончания отправки. Results закрывает координатор после завершения всех workers, а не один worker.

Для простого лимита параллельных независимых задач можно использовать buffered channel как semaphore или `errgroup.SetLimit`.

---

## Развёрнутый ответ сеньора: все тонкости

Worker count выбирают по bottleneck. CPU-bound работа часто ограничивается около доступного параллелизма; I/O-bound может иметь больше workers, но реальные лимиты задают connection pool, rate limit внешнего сервиса, память и latency. Настройку подтверждают нагрузочным тестом.

Bounded queue — часть overload policy. Когда она заполнена, можно блокировать producer (backpressure), отклонить запрос, удалить старое/новое сообщение или сбросить на устойчивый broker. Молчаливое создание goroutine в обход очереди разрушает лимит.

Нужно определить семантику ошибок: fail-fast с отменой, собрать все ошибки, частичный результат или retry. Retry внутри worker должен иметь backoff, jitter, лимит попыток и учитывать идемпотентность; иначе pool усиливает аварию внешней системы.

Справедливость, порядок результатов и порядок задач — отдельные требования. Несколько workers обычно нарушают порядок. Если порядок важен, добавляют sequence и reorder buffer либо шардируют по ключу.

Graceful shutdown должен прекратить приём, решить судьбу очереди и дождаться workers в пределах deadline. Закрытие jobs при активных senders вызывает panic, поэтому владелец очереди должен быть один.

## Если забыл / Простыми словами

Worker pool — **N обработчиков + ограниченная очередь + политика перегрузки**. Обязательно проговори лимит ресурса, backpressure, cancellation, ошибки и владельца закрытия каналов.

### Аналогия и объяснение

Представь runtime как диспетчера, который распределяет работу и память между множеством исполнителей. Если не учитывать правила диспетчера, задачи могут мешать друг другу, ждать бесконечно или расходовать ресурсы. Поэтому всегда нужно понимать владельца состояния, момент синхронизации и условие завершения.
