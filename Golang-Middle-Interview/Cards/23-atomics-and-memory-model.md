# Когда использовать atomic и что такое happens-before?

## Вопрос

Что гарантируют операции `sync/atomic`, чем атомарность отличается от отсутствия гонки и что означает happens-before?

## Краткий ответ

Atomic гарантирует неделимую и синхронизированную операцию над конкретной ячейкой. Happens-before — отношение, при котором записи одной goroutine обязаны быть видны другой. Набор атомарных полей не делает составной инвариант атомарным; для него обычно нужен mutex.

## Развёрнутый ответ мидла

```go
var n atomic.Int64
n.Add(1)
fmt.Println(n.Load())
```

Типизированные атомики уменьшают риск неверного адреса и выравнивания. Подходят для счётчиков, флагов, версий и публикации immutable snapshot через `atomic.Pointer`/`atomic.Value`.

Обычная конкурентная запись и чтение `int` без синхронизации — data race, даже если на данной архитектуре машинное слово физически читается «целиком».

Синхронизацию создают, среди прочего, mutex, send/receive и close каналов, атомарные операции. Простое «сначала присвоили data, потом bool» без синхронизации не гарантирует видимость в другой goroutine.

## Развёрнутый ответ сеньора: все тонкости

Memory model следует использовать как минимальный контракт, а не как оправдание трюков на конкретном CPU. Если чтение не упорядочено после записи через happens-before, программа с конфликтующим доступом имеет race и её поведение нельзя рассуждать обычной последовательной моделью.

Атомики Go предоставляют сильную согласованность для атомарных операций согласно документации memory model. Но логическая операция `if !loaded { initialize(); loaded = true }` содержит несколько шагов и требует протокола (`Once`, CAS-loop, mutex).

CAS-loop должен корректно повторять чтение, учитывать contention и не выполнять необратимый side effect до успешного CAS без компенсации. Lock-free не означает wait-free и не гарантирует лучшую производительность. Под высокой конкуренцией cache-line bouncing может сделать atomic-счётчик узким местом.

`atomic.Value` требует, чтобы все `Store` использовали один конкретный тип; хранение `nil` и несогласованных типов имеет ограничения. Публикуемый объект после Store обычно рассматривают как immutable, иначе atomic защищает только указатель, а не содержимое.

На 32-битных платформах исторически важны alignment и 64-битные операции; типизированные atomic-типы помогают обеспечить правильное размещение. Не смешивают atomic и неатомарный доступ к одной переменной.

## Если забыл: что это, зачем и где нужно

Atomic хорош для **одной простой ячейки и ясного протокола**. Если нужно одновременно согласовать несколько полей, выбери mutex. Happens-before отвечает не «что случилось по часам», а «какие записи обязаны быть видны».

## Подробное объяснение простыми словами

Представь runtime как диспетчера, который распределяет работу и память между множеством исполнителей. Если не учитывать правила диспетчера, задачи могут мешать друг другу, ждать бесконечно или расходовать ресурсы. Поэтому всегда нужно понимать владельца состояния, момент синхронизации и условие завершения.
