# Что такое data race и как её искать?

## Вопрос

Чем data race отличается от race condition, как работает `go test -race` и гарантирует ли чистый прогон отсутствие гонок?

## Краткий ответ

Data race — конкурентные доступы к одной памяти, хотя бы один из которых запись, без требуемой синхронизации. Race condition шире: результат зависит от порядка событий и может существовать даже без data race. `-race` динамически обнаруживает только исполненные конфликтующие пути.

## Развёрнутый ответ мидла

Типичная гонка:

```go
var n int
go func() { n++ }()
fmt.Println(n)
```

Исправляют mutex, atomic, каналом или передачей владения одной goroutine. Ожидание через `time.Sleep` синхронизацией не является.

Команды:

```bash
go test -race ./...
go test -race -count=10 ./...
go run -race ./cmd/service
```

Race detector показывает стеки конфликтующих доступов и места создания goroutine. Тест должен воспроизвести путь, иначе детектор его не увидит.

Логическая гонка без data race: две корректно синхронизированные операции отдельно проверяют остаток и списывают деньги, но между ними другая операция меняет состояние.

## Развёрнутый ответ сеньора: все тонкости

Детектор инструментирует память и имеет заметные накладные расходы по CPU и памяти, поэтому обычно запускается в CI/тестовой среде, а не постоянно в production. Он не является статическим доказательством и не видит все взаимодействия с неинструментированным кодом/некоторым внешним runtime.

Даже типы, безопасные для конкурентного использования, не делают безопасной последовательность операций. Например, два отдельных `Load`/`Store` могут не поддерживать бизнес-инвариант; нужна транзакция под lock или CAS-протокол.

Частая скрытая гонка — возврат внутреннего `map`/slice после unlock, изменение pointer target, переиспользование буфера после отправки, захват loop variable в коде со старыми правилами версий языка. Нужно учитывать версию `go` в `go.mod`: семантика переменных range менялась.

Исправление должно устанавливать понятный happens-before, а не просто снижать вероятность пересечения. Копирование данных и immutable snapshots часто проще глобальной блокировки.

Race report нельзя бездумно «лечить» добавлением lock рядом с одной строкой: все доступы к одному инварианту должны следовать одному протоколу, иначе гонка или логическая ошибка останется.

## Если забыл: что это, зачем и где нужно

Data race — **одна память + конкурентные доступы + запись + нет синхронизации**. Запускай `-race`, но помни: он проверил только реально выполненные пути. Race condition — более широкая логическая проблема.

## Подробное объяснение простыми словами

Data race — **одна память + конкурентные доступы + запись + нет синхронизации**. Запускай `-race`, но помни: он проверил только реально выполненные пути. Race condition — более широкая логическая проблема.

Представь runtime как диспетчера, который распределяет работу и память между множеством исполнителей. Если не учитывать правила диспетчера, задачи могут мешать друг другу, ждать бесконечно или расходовать ресурсы. Поэтому всегда нужно понимать владельца состояния, момент синхронизации и условие завершения.
