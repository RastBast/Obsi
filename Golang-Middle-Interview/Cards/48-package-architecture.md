# Как разделять Go-сервис на пакеты?

## Вопрос

По каким принципам выбирать package boundaries, где размещать `cmd`, `internal`, domain и adapters, и как избегать import cycles?

## Краткий ответ

Пакеты группируют по связному поведению и стабильным границам, а не механически по слоям/типам файлов. Зависимости направляют к устойчивым контрактам; интерфейс часто объявляет потребитель. `cmd` собирает приложение, `internal` скрывает непубличный код. Цикл импортов — сигнал пересмотреть ответственность.

## Развёрнутый ответ мидла

Частый каркас, но не обязательный стандарт:

```text
cmd/api/main.go        — composition root
internal/order/...     — бизнес-возможность
internal/postgres/...  — adapter хранения
internal/httpapi/...   — transport
```

`main` читает конфигурацию, создаёт конкретные зависимости, запускает и останавливает сервис. Бизнес-логика не должна импортировать HTTP handler или конкретный SQL driver без необходимости.

Название package короткое и отражает сущность/возможность, без `utils`, `common`, `models` как свалки. Публичный API минимален; внутренние детали не экспортируют.

## Развёрнутый ответ сеньора: все тонкости

Нет официально обязательного «standard Go project layout». Копирование огромной clean architecture для маленького сервиса создаёт ceremony и интерфейсы без вариантов. Архитектура должна соответствовать скорости изменения и реальным границам команды/домена.

Import cycle решают не переносом всего в `common`, а анализом направления зависимости: выделить общую модель с ясным владельцем, инвертировать маленький интерфейс на стороне consumer, объединить искусственно разделённые пакеты или передавать данные на границе.

Domain types и transport/storage DTO могут совпадать в простом CRUD, но при разных контрактах разделение защищает инварианты. Слишком много mapping тоже имеет цену. Решение зависит от независимости изменений.

Пакет должен быть тестируемым через публичное поведение и не требовать скрытого global state/init. Конфигурация и lifecycle — явные зависимости. Interfaces нужны на volatility boundary, а не между каждым слоем автоматически.

Экспорт — долгосрочное обещание даже внутри большого mono-repo. `internal` даёт компиляторную границу, но чрезмерно глубокие деревья ухудшают навигацию. Циклические runtime-зависимости через callbacks/events тоже могут существовать без import cycle и требуют архитектурного контроля.

## Если забыл: что это, зачем и где нужно

Пакет — единица **связности, компиляции и API**. Делай зависимости однонаправленными, собирай concrete implementations в `main`, не создавай `utils`-свалку и не применяй шаблон сложнее задачи.
