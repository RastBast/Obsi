# Как писать корректные benchmark в Go?

## Вопрос

Как устроен `testing.B`, что означают `ns/op`, `B/op`, `allocs/op` и как избежать измерения setup вместо целевого кода?

## Краткий ответ

Benchmark многократно выполняет операцию, а harness подбирает число итераций. Setup выносят из измеряемого участка или используют timer control. `ReportAllocs` показывает память. Результаты сравнивают статистически в одинаковой среде, не по одному запуску.

## Развёрнутый ответ мидла

```go
func BenchmarkParse(b *testing.B) {
    input := []byte(`{"id":42}`)
    b.ReportAllocs()
    for i := 0; i < b.N; i++ {
        _, err := Parse(input)
        if err != nil { b.Fatal(err) }
    }
}
```

Запуск:

```bash
go test -bench=Parse -benchmem -count=10 ./...
```

- `ns/op` — время операции;
- `B/op` — выделенные байты;
- `allocs/op` — число аллокаций.

Если setup дорогой и не является частью измерения, используют `b.StopTimer/StartTimer`, `ResetTimer` или современный iterator API доступной версии Go.

## Развёрнутый ответ сеньора: все тонкости

Компилятор может удалить вычисление, результат которого не наблюдается. Результат сохраняют так, чтобы операция оставалась видимой, но не создают искусственную глобальную contention без необходимости. Нужно проверять, что benchmark измеряет реальный production path и не включает случайный parsing/setup.

CPU frequency scaling, фоновые процессы, thermal throttling, GC и scheduler создают шум. Сравнивают old/new через `benchstat`, одинаковый toolchain, hardware и параметры; смотрят доверие/распределение, а не процент одного прогона.

Для конкурентного кода есть `RunParallel`, но он моделирует специфический contention и не заменяет нагрузочный тест end-to-end. Размеры входа должны включать типичные и граничные случаи; алгоритм может выигрывать на 10 элементах и проигрывать на 100k.

`B/op` считает heap allocations, видимые инструменту, а не весь RSS или стоимость GC. Оптимизация одной метрики может ухудшить latency, читаемость или удержание памяти.

Benchmark внутри package может измениться от inlining и escape context. Для API полезны и microbenchmarks, и macro/load tests. Перед оптимизацией строят профиль, иначе можно ускорить участок, занимающий 1% времени.

## Если забыл: что это, зачем и где нужно

Хороший benchmark: **одна понятная операция, setup вне timer, результат не удалён, `-benchmem`, много прогонов и статистическое сравнение**. Цифра без среды и дисперсии почти ничего не доказывает.

Представь, что это одно из правил языка и стандартной библиотеки: оно задаёт, как программа хранит данные или выполняет действие. Понимание правила помогает не угадывать поведение кода, а заранее предсказывать результат, находить ошибки и выбирать более простой API.
