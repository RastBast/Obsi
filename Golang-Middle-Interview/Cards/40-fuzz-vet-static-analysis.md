# Что дают fuzzing, go vet и статический анализ?

## Вопрос

Как встроенный fuzzing дополняет unit tests, что проверяет `go vet` и почему ни один анализатор не доказывает корректность программы?

## Краткий ответ

Fuzzing генерирует входы и ищет panic, нарушение инвариантов и расхождения; найденные случаи сохраняются как regression corpus. `go vet` ловит подозрительные конструкции, которые компилируются, но часто ошибочны. Статические анализаторы и race detector покрывают разные классы проблем.

## Развёрнутый ответ мидла

```go
func FuzzParse(f *testing.F) {
    f.Add([]byte("42"))
    f.Fuzz(func(t *testing.T, data []byte) {
        v, err := Parse(data)
        if err == nil {
            out := Encode(v)
            v2, err := Parse(out)
            if err != nil || !reflect.DeepEqual(v, v2) {
                t.Fatalf("round trip failed")
            }
        }
    })
}
```

Seed corpus задаёт полезные стартовые классы. Fuzz target должен быть детерминированным, быстрым и ограничивать чрезмерное потребление памяти/времени входом.

Базовый CI-набор обычно включает `go test ./...`, `go test -race ./...` по политике, `go vet ./...`, форматирование и дополнительные линтеры/`govulncheck`.

## Развёрнутый ответ сеньора: все тонкости

Сильный fuzz test проверяет свойство, а не только «не паникует»: round trip, идемпотентность, эквивалентность двух реализаций, сохранение инварианта. Он особенно полезен для parser, protocol, serialization, Unicode и security boundaries.

Найденный crash минимизируется и сохраняется; его стоит превратить в понятный regression test/seed. Corpus и время fuzzing балансируют с размером CI artifacts. Fuzzing не заменяет ручные сценарии бизнес-логики.

`go vet` — набор эвристических анализаторов, а не linter стиля. Он ищет, например, неверные printf-аргументы, копирование lock и подозрительные конструкции. Дополнительные линтеры могут конфликтовать и давать false positives; правила фиксируют по версии и документируют исключения.

`govulncheck` анализирует известные уязвимости с учётом достижимых вызовов, но база и статический анализ не видят zero-day и runtime-конфигурацию. Dependency scanning — слой, не гарантия.

Staticcheck, custom `go/analysis`, fuzzing, unit/integration tests и race detector дополняют друг друга: первый рассуждает без запуска, fuzz исследует входы, race видит исполненные конкурентные доступы.

## Если забыл: что это, зачем и где нужно

Unit test проверяет выбранные примеры, fuzzing ищет неожиданные входы, vet ищет подозрительный код без выполнения. Лучший ответ — **комбинировать слои и сохранять каждый найденный баг как regression**.
