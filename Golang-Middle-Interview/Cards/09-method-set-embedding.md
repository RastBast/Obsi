# Как method set и embedding влияют на реализацию интерфейсов?

Какие методы принадлежат `T` и `*T`, что происходит при встраивании типа и является ли embedding наследованием?

===

@input

---

## Краткий ответ

Method set `T` содержит методы с receiver `T`; method set `*T` — методы с receiver `T` и `*T`. Встраивание продвигает методы встроенного поля, но это композиция, а не наследование и не подтипирование.

---

## Развёрнутый ответ мидла

```go
type Runner interface{ Run() }
type Job struct{}
func (*Job) Run() {}

var _ Runner = (*Job)(nil) // compile-time проверка
// var _ Runner = Job{}    // не компилируется
```

При вызове `j.Run()` компилятор может автоматически взять адрес адресуемой переменной, но при присваивании интерфейсу проверяется именно method set.

```go
type Logger struct{}
func (Logger) Log(string) {}

type Service struct {
    Logger // embedded field
}
```

`Service` получает продвинутый метод `Log`, но поле всё ещё можно явно вызвать как `s.Logger.Log(...)`. При конфликте имён нужен явный выбор.

---

## Развёрнутый ответ сеньора: все тонкости

Правила продвижения зависят от того, встроено значение `T` или указатель `*T`, и рассматривается method set внешнего `S` или `*S`. Практически это проверяют compile-time assertions для нужных форм, а не полагаются на память:

```go
var _ io.Reader = (*MyType)(nil)
```

Embedding не устанавливает отношение «is-a». `Service` нельзя использовать как `Logger` без явного обращения к полю; нет виртуального dispatch по переопределённому методу как в классическом ООП. Метод встроенного типа, вызывающий другой свой метод, не перенаправляется автоматически на одноимённый метод внешнего типа.

Встраивание интерфейсов создаёт объединение требований и удобно для составных интерфейсов. Но большие интерфейсы повышают связанность; часто потребителю достаточно одного-двух методов.

Встраивание конкретного типа в публичную структуру фактически продвигает его методы в ваш API. Добавление метода во вложенный тип может породить конфликт или неожиданно изменить реализацию интерфейса. Для стабильного API именованное поле иногда безопаснее embedding.

Нулевое встроенное поле-указатель может привести к panic при вызове продвинутого метода, если тот разыменует receiver. Конструктор или явная проверка должны поддерживать инвариант.

## Если забыл / Простыми словами

Запомни таблицу: **T — только методы T; *T — методы T и *T**. Embedding означает «включить и продвинуть поведение», но не наследование. Это важно при компиляционных ошибках реализации интерфейса и проектировании API.

### Аналогия и объяснение

Представь, что это одно из правил языка и стандартной библиотеки: оно задаёт, как программа хранит данные или выполняет действие. Понимание правила помогает не угадывать поведение кода, а заранее предсказывать результат, находить ошибки и выбирать более простой API.
