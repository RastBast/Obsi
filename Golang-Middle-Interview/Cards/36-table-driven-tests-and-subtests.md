# Как писать table-driven tests и subtests?

## Вопрос

Почему в Go популярны табличные тесты, как использовать `t.Run`, `t.Helper`, `t.Cleanup` и параллельные subtests без гонок?

## Краткий ответ

Таблица отделяет сценарии от общей логики проверки, `t.Run` даёт именованные изолированные subtests. Helpers улучшают место ошибки, Cleanup гарантирует уборку. Для `t.Parallel` тестовые данные и внешние ресурсы должны быть независимыми.

## Развёрнутый ответ мидла

```go
func TestParse(t *testing.T) {
    tests := []struct {
        name string
        in   string
        want int
        ok   bool
    }{
        {"number", "42", 42, true},
        {"bad", "x", 0, false},
    }

    for _, tt := range tests {
        tt := tt
        t.Run(tt.name, func(t *testing.T) {
            got, err := Parse(tt.in)
            if (err == nil) != tt.ok { t.Fatalf("err=%v", err) }
            if got != tt.want { t.Errorf("got %d, want %d", got, tt.want) }
        })
    }
}
```

`Fatal/Fatalf` прекращает текущий test goroutine, `Error/Errorf` продолжает. Helper-функция вызывает `t.Helper()`. Временные файлы создают через `t.TempDir`, env — `t.Setenv`, уборку — `t.Cleanup`.

## Развёрнутый ответ сеньора: все тонкости

Нужно учитывать версию языка: семантика loop variables для range изменилась в новых Go modules. Явное `tt := tt` остаётся понятным для совместимости, но важно уметь объяснить, почему в конкретной версии оно нужно или избыточно.

`t.Parallel` отмечает тест как параллельный и приостанавливает до завершения последовательной части родителя. Общая БД, env, global clock, фиксированный порт и package globals делают тесты flaky. `t.Setenv` несовместим с параллельными тестами, влияющими на process-wide environment.

Проверять нужно наблюдаемый контракт, а не внутренние вызовы. Хорошее сообщение показывает `got`, `want` и вход; для больших структур полезен diff. Ошибки проверяют `errors.Is/As`, а не полный текст, если текст не является контрактом.

Таблица не обязательна: сценарий с существенно разной подготовкой и проверками яснее как отдельные тесты. Огромная структура callbacks может скрыть смысл.

Детерминизм важнее покрытия: часы, случайность, сеть и IDs внедряют как зависимости или контролируют. Integration tests отделяют build tags/окружением и всё равно ограничивают timeout.

## Если забыл: что это, зачем и где нужно

Шаблон: **name, input, want → `t.Run` → Arrange/Act/Assert**. Изолируй состояние, делай полезные ошибки и включай `t.Parallel` только когда независимость доказана.

## Подробное объяснение простыми словами

Представь, что это одно из правил языка и стандартной библиотеки: оно задаёт, как программа хранит данные или выполняет действие. Понимание правила помогает не угадывать поведение кода, а заранее предсказывать результат, находить ошибки и выбирать более простой API.
