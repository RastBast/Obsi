# Почему interface с nil-указателем не равен nil?

## Вопрос

Из чего логически состоит interface в Go и почему значение интерфейса с типизированным `nil` внутри не равно `nil`?

## Краткий ответ

Интерфейс логически хранит динамический тип и динамическое значение. Он равен `nil`, только когда оба отсутствуют. Если положить `(*MyError)(nil)`, динамический тип уже есть, поэтому интерфейс ненулевой.

## Развёрнутый ответ мидла

```go
type MyError struct{}
func (*MyError) Error() string { return "boom" }

func f() error {
    var e *MyError = nil
    return e
}

fmt.Println(f() == nil) // false
```

Правильнее возвращать литеральный `nil`, если ошибки нет:

```go
func f() error {
    if ok { return nil }
    return &MyError{}
}
```

Интерфейсы обеспечивают полиморфизм неявно: тип реализует интерфейс, если имеет требуемый набор методов. Обычно интерфейсы объявляют на стороне потребителя и делают маленькими.

Сравнение двух интерфейсов возможно, но вызовет panic, если их одинаковый динамический тип несравним, например срез.

## Развёрнутый ответ сеньора: все тонкости

Упрощённая модель `(dynamic type, dynamic value)` полезнее заучивания runtime-структур, которые являются деталями реализации. Пустой интерфейс `any` может хранить любое значение; непустой дополнительно связывает тип с таблицей методов. Конкретная упаковка может вызвать escape/аллокацию, но это решает компилятор, и вывод проверяют `-gcflags=-m` и профилем.

Typed nil встречается не только с указателями, но и с map, slice, channel и function. Внутри `any` они делают интерфейс ненулевым. При этом конкретную nil-map можно читать, а nil-function при вызове паникует — поведение зависит от динамического типа.

Метод с pointer receiver может быть вызван через интерфейс, содержащий nil-указатель. До входа в метод автоматической panic нет; panic возникнет, если метод разыменует receiver. Это иногда используют намеренно, но чаще такой API усложняет контракт.

Интерфейсы стоит проектировать по требуемому поведению, а не как копии всех методов реализации. Принимают интерфейс, возвращают конкретный тип — полезная эвристика, но не абсолютный закон. Слишком раннее введение интерфейса «на всякий случай» ухудшает навигацию и тестирование вместо пользы.

## Если забыл: что это, зачем и где нужно

Представь interface как пару **(тип, значение)**. Только `(nil, nil)` равен `nil`; `(*T, nil)` — нет. Это одна из самых частых ловушек с `error` и моками.
