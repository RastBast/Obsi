# Как реализовать rate limiting и защиту от перегрузки?

## Вопрос

Чем token bucket отличается от semaphore, где ставить rate limit и какие ответы/метрики нужны при перегрузке?

## Краткий ответ

Token bucket ограничивает скорость во времени и допускает burst; semaphore ограничивает число одновременных операций. Rate limit применяют по осмысленному ключу и на нужной границе, возвращают явный отказ (`429`/`503`) с retry hints вместо неограниченной очереди.

## Развёрнутый ответ мидла

Token bucket пополняется с заданной скоростью до capacity; запрос тратит token. В Go можно использовать `golang.org/x/time/rate`:

```go
lim := rate.NewLimiter(rate.Limit(100), 200)
if !lim.Allow() {
    // 429 Too Many Requests
}
```

`Allow` отказывает сразу, `Wait(ctx)` ждёт token с учётом отмены, `Reserve` позволяет спланировать ожидание и требует корректной отмены reservation при отказе.

Semaphore защищает, например, максимум 20 дорогих запросов одновременно независимо от RPS. Часто нужны оба ограничения плюс bounded queue.

## Развёрнутый ответ сеньора: все тонкости

Ключ лимита определяет справедливость: IP легко делится NAT и подделывается без trusted proxy policy; user/API key требует аутентификации; tenant может иметь weighted quota. Map лимитеров должна удалять неактивные ключи, иначе это memory leak/DoS по cardinality.

Локальный limiter ограничивает каждый instance отдельно; при autoscaling общий лимит меняется. Для глобальной квоты используют централизованный/распределённый алгоритм или делят budget, принимая компромисс точности, latency и доступности. Жёсткая глобальная точность часто дорога.

Очередь тоже является нагрузкой: длинная очередь увеличивает tail latency и удерживает память/соединения. Load shedding должен происходить до дорогой работы. Adaptive concurrency может реагировать на latency/saturation, но требует стабильных сигналов и защиты от осцилляций.

`429` означает клиентскую/квотную частоту, `503` — временную неспособность сервиса; `Retry-After` помогает, но клиенты должны добавлять jitter. Приоритеты и отдельные pools не дают batch-трафику вытеснить control-plane/health.

Метрики: allowed/rejected/wait duration по bounded dimensions, queue depth, in-flight, saturation и downstream latency. Нельзя label-ить каждым user ID.

## Если забыл: что это, зачем и где нужно

**Rate limiter ограничивает поток во времени; semaphore — одновременность; bounded queue — ожидание.** Вместе они создают backpressure. Лучше быстро и явно отказать, чем принять работу, которую сервис не успеет выполнить.

## Подробное объяснение простыми словами

**Rate limiter ограничивает поток во времени; semaphore — одновременность; bounded queue — ожидание.** Вместе они создают backpressure. Лучше быстро и явно отказать, чем принять работу, которую сервис не успеет выполнить.

Представь запрос как посылку, проходящую через несколько узлов. На каждом участке она может задержаться, потеряться или быть обработана повторно. Поэтому сетевой код обязан ограничивать ожидание, проверять результат и безопасно переживать частичные сбои.
