# Кто и когда должен закрывать канал?

## Вопрос

Что происходит при отправке и получении из закрытого канала, как работает `range` и кто отвечает за `close`?

## Краткий ответ

Обычно канал закрывает отправитель, когда новых значений точно не будет. Получение после опустошения сразу возвращает zero value и `ok=false`; отправка или повторный `close` вызывают panic. `range` читает до закрытия и опустошения.

## Развёрнутый ответ мидла

```go
for v := range ch {
    use(v)
}

v, ok := <-ch
if !ok { /* канал закрыт и пуст */ }
```

`close` не очищает уже буферизованные элементы: сначала получатели заберут их, затем начнут получать zero value с `ok=false`.

Закрытие — broadcast-сигнал для получателей: все ожидающие разблокируются. Но закрывать канал только ради остановки не всегда нужно; `context` часто лучше выражает отмену.

Receiver обычно не закрывает канал, потому что не знает, будут ли ещё отправители. При нескольких producer их координируют, например `WaitGroup`, а канал закрывает отдельный владелец после завершения всех.

## Развёрнутый ответ сеньора: все тонкости

«Закрывает отправитель» — эвристика владения, точнее: закрывает компонент, который может доказать отсутствие будущих send. У канала с несколькими независимыми отправителями ни один producer обычно не обладает этим знанием.

Проверка «закрыт ли канал» перед send не решает гонку: состояние может измениться сразу после проверки. Универсальной безопасной `isClosed` нет. `recover` вокруг send — плохой протокол. Нужна архитектура с одним владельцем закрытия и согласованным прекращением producers.

Закрытие канала создаёт синхронизационное событие: закрытие happens-before получения, которое наблюдает закрытое состояние. Это позволяет публиковать неизменяемые данные перед broadcast, если строго соблюдён протокол.

Nil-channel нельзя закрывать — будет panic. Получение и отправка на nil-channel блокируются навсегда. Закрытый канал всегда готов для receive в `select`, поэтому после обнаружения закрытия его часто присваивают `nil`, чтобы отключить ветку и избежать busy loop.

Канал ошибок не обязательно закрывать, если потребитель получает ровно один результат. Закрытие — не освобождение ресурса в стиле файла; GC соберёт недостижимый канал. Оно сообщает именно «значений больше не будет».

## Если забыл: что это, зачем и где нужно

Закрытие — не удаление канала, а сигнал **EOF для потока значений**. Запомни: receive → zero/false, send → panic, close второй раз → panic, закрывает владелец производства.

## Подробное объяснение простыми словами

Закрытие — не удаление канала, а сигнал **EOF для потока значений**. Запомни: receive → zero/false, send → panic, close второй раз → panic, закрывает владелец производства.

Представь runtime как диспетчера, который распределяет работу и память между множеством исполнителей. Если не учитывать правила диспетчера, задачи могут мешать друг другу, ждать бесконечно или расходовать ресурсы. Поэтому всегда нужно понимать владельца состояния, момент синхронизации и условие завершения.
