# Как правильно использовать context.Context?

Для чего нужен `context.Context`, как его передавать, где вызывать cancel и какие данные нельзя класть в context?

===

@input

---

## Краткий ответ

Context переносит дедлайн, сигнал отмены и request-scoped значения через цепочку вызовов. Его передают первым параметром, не хранят в структуре без особой причины и не передают `nil`. Создатель cancellable context обязан вызвать `cancel`.

---

## Развёрнутый ответ мидла

```go
func Load(ctx context.Context, id string) (User, error) { /* ... */ }

ctx, cancel := context.WithTimeout(parent, 2*time.Second)
defer cancel()
user, err := Load(ctx, id)
```

Операция должна периодически наблюдать `ctx.Done()` или передавать context в API, которое это делает. Причину проверяют через `ctx.Err()` — `context.Canceled` или `context.DeadlineExceeded`.

В `context.Value` кладут только данные области запроса: trace ID, auth principal и подобное. Конфигурация, logger как обязательная зависимость и параметры функции не должны прятаться в context. Ключи делают собственным несравнимо-конфликтующим типом, обычно неэкспортируемым.

---

## Развёрнутый ответ сеньора: все тонкости

Отмена кооперативна: context не «убивает» goroutine. Если код блокируется в операции без поддержки context или игнорирует `Done`, он продолжит работать. Для CPU-цикла нужны разумные точки проверки, но проверка на каждой инструкции тоже избыточна.

`defer cancel()` освобождает timer и ссылки дочернего context, даже если дедлайн не наступил. Дочерний context не должен переживать родительский без осознанного решения. Для редких задач, которые должны отделиться от отмены запроса, современные версии предлагают `context.WithoutCancel`, но значения и отсутствие дедлайна нужно оценивать с точки зрения безопасности и lifecycle.

`WithCancelCause`/`Cause` позволяют сохранить доменную причину отмены, не заменяя обычную обработку результата операции. При одновременных причинах важна первая зафиксированная отмена.

Не стоит начинать с `context.Background()` глубоко в библиотеке: так теряются дедлайны вызывающего кода. Корневые context создают на верхнем уровне (`main`, handler, job runner), ниже — наследуют.

Context безопасен для одновременного использования несколькими goroutine. Значения должны быть immutable или отдельно синхронизироваться. Нельзя помещать в context секреты, если логирующая/telemetry-инфраструктура может их раскрыть.

## Если забыл / Простыми словами

Context — провод для **отмены, дедлайна и request-scoped metadata**, а не универсальный пакет параметров. Запомни сигнатуру `func(ctx context.Context, ...)`, наследование от родителя и `defer cancel()`.
